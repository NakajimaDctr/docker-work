## Q. Dockerfile.multiとDockerfile.singleで出来上がるイメージは違うのに、docker runで同じ出力が得られるのはなぜ?

**A.**
両方とも最終的に実行するのは**同じ`go build`の成果物(バイナリ`app`)**だから。`docker run`で動く「アプリケーションの中身」は同一で、違うのは**その周りに何が同梱されているか**だけ。

| | Dockerfile.single | Dockerfile.multi |
|---|---|---|
| 実行されるプログラム | `/src/app`(goでビルドしたバイナリ) | `/app`(同じソースからビルドした同じバイナリ) |
| イメージの中身 | Goのコンパイラ・ツール一式 + ソースコード + バイナリ(golang:1.22ベース) | バイナリだけ(alpine:3.19ベース) |
| イメージサイズ | 大きい(1GB近い) | 小さい(alpine + バイナリで数十MB) |

`CMD`が実行するのは「コンパイル済みのバイナリを起動する」という処理であり、標準出力に何を表示するかはそのGoプログラムのロジックそのものに書かれている。ビルドに使ったツールチェーンや、周囲に残っているソースコード・キャッシュなどの余分なものは実行結果(stdout)には一切影響しない。

### ポイント

- `docker run`の出力 = アプリのロジックの結果であり、イメージに何が同梱されているかとは無関係。
- multi-stage buildは「ビルドに必要なもの」と「実行に必要なもの」を分離し、`COPY --from=builder`で成果物だけを軽量イメージに持ち込む仕組み。
- alpineベースのイメージにはGoツールチェーンもソースコードも残っておらず、`COPY --from=builder`でコピーしたバイナリだけが存在する。実行時に必要なのはコンパイル済みバイナリだけなので、それ以外を全部削ぎ落としても同じ動作をする。

```dockerfile
# ステージ1: ビルド用(重い、ツール一式入り)
FROM golang:1.22 AS builder
WORKDIR /src
COPY . .
RUN go build -o app .

# ステージ2: 実行用(軽量ベースイメージ)
FROM alpine:3.19
COPY --from=builder /src/app /app
CMD ["/app"]
```
