# 学習メモ・QA集

このファイルは、06章「Docker Composeの基本」を学習する中で出た疑問と回答をQA形式でまとめたメモです。

---

## Q. `build: .` とは何か? どういう時にbuildが必要か?

**A.**
`build: .` は「この`docker-compose.yml`があるディレクトリ(`.`)にあるDockerfileを使って、イメージをその場でビルドする」という指示。`.`はビルドコンテキスト(Dockerfileや`COPY`元ファイルを探す起点ディレクトリ)を指す。

```yaml
services:
  web:
    build: .              # 自分で書いたDockerfileからビルドする
  redis:
    image: redis:7-alpine  # 既製イメージをそのまま使う
```

- `build:` … ローカルのDockerfileからイメージをビルドする。自分たちのアプリコードのように、Docker Hubに既製イメージが存在しないものに使う。
- `image:` … 既にある(公開/自作)イメージを取得してそのまま使う。DB・キャッシュなど既製ミドルウェアに使う。

buildが必要になるのは主に以下のケース。

1. 自分たちのアプリのコード(既製イメージが存在しないもの)をコンテナ化する時
2. Dockerfileの内容やアプリのコード・依存パッケージを変更した後の再ビルド(`docker compose up --build`)
3. 既製イメージをベースに、独自のカスタマイズを加えたイメージを作る時

逆に、既に完成した既製イメージをそのまま使うだけなら`build`は不要で`image:`だけで済む。

## Q. `ports: - "8080:5000"` はホスト側で`curl http://localhost:8080`するとコンテナ内の5000へフォワードされるということか?

**A.**
その理解で正しい。書式は`"ホスト側ポート:コンテナ側ポート"`。

1. ホスト側の`curl http://localhost:8080`がDockerホストの8080番に届く
2. Dockerが自動的にそれをコンテナ内部の5000番へフォワードする
3. コンテナ内でリッスンしているアプリ(`app.run(host="0.0.0.0", port=5000)`)がリクエストを受け取る

ホスト側とコンテナ側のポートをあえて分けているのは、コンテナ内のアプリコードを変更せずに外部公開ポートだけ自由に変えられ、同じホスト上で複数コンテナを動かす際にホスト側ポートの衝突だけ気にすればよくなるため。

補足: コンテナ間通信(例: `web`→`redis`)は`ports`と無関係。同じdocker composeネットワーク内のコンテナ同士は、`ports`で公開していなくてもコンテナ名(サービス名)と内部ポートで直接通信できる。`ports`はあくまで「ホストの外からコンテナにアクセスするための入り口」。

## Q. `docker compose up`のログに`http://127.0.0.1:5000`と`http://172.18.0.3:5000`の2行が出るのは、5000ポートで受け付けるアプリが異なるコンテナで2つ起動しているということか?

**A.**
いいえ、コンテナは1つ。同じ`web`コンテナ内で動いている1つのFlaskプロセスが出しているログ。

`app.run(host="0.0.0.0", port=5000)`の`host="0.0.0.0"`は「コンテナ内のすべてのネットワークインターフェースで待ち受ける」という意味で、Flaskの開発サーバーは起動時に自分がどのアドレスからアクセスされ得るかを列挙してログに出す。

- `127.0.0.1` … コンテナ自身の中からアクセスする時のアドレス(ループバック)
- `172.18.0.3` … このコンテナに割り当てられた、docker composeのプライベートネットワーク上のIPアドレス

どちらも同じプロセス・同じポート5000への入り口が2つ表示されているだけで実体は1つ。本当に2つのコンテナが起動していれば`docker compose ps`で`web-1`と`web-2`のように別々のコンテナ名・IDが表示される。

## Q. `docker-compose.yml`1つにつき1つのコンテナが起動する?

**A.**
いいえ。1つの`docker-compose.yml`につき、その中で定義した`services`の数だけコンテナが起動する。

```yaml
services:
  web:                  # サービス1 → web-1
    build: .
    ports:
      - "8080:5000"
    depends_on:
      - redis

  redis:                # サービス2 → redis-1
    image: redis:7-alpine
```

- `docker-compose.yml`1ファイル … 複数サービスをまとめる、アプリ全体の設計図
- `services:`配下の1エントリ … 通常1コンテナに対応

コンテナ名は`<サービス名>-<連番>`という命名規則(例: `web-1`)。`docker compose up --scale web=3`のように明示的にスケール指定すれば、1つのサービスから複数コンテナ(`web-1`, `web-2`, `web-3`)を起動することもできる。

## Q. `127.0.0.1:5000`はコンテナ内部からFlaskアプリ自身を呼ぶ時、`172.18.0.3:5000`はredisからFlaskアプリのコンテナを呼ぶ時、という理解で合っているか?

**A.**
`127.0.0.1`側は正しい。`172.18.0.3`側は2点補足が必要。

- **127.0.0.1** … 同じコンテナ内のプロセスが自分自身の5000番ポートを呼ぶ時に使う。ループバックアドレスは同じネットワーク名前空間(=同じコンテナ)内からしか到達できない。
- **172.18.0.3** … このアプリでは`redis`が`web`を呼ぶコードは存在しない(通信は`web`→`redis`の一方向のみ)ため、実際には使われていない。また、このIPは`redis`専用の入り口ではなく、同じdocker composeネットワークに属するコンテナなら誰でもアクセスできるアドレス。

実務上は生のIPを直接指定することはほぼなく、docker composeが提供するDNS機能でサービス名(`redis`, `web`)をそのまま使う。

## Q. 同じdocker composeネットワークに属するサービス = 同じ`docker-compose.yml`で定義されたサービス、で合っているか?

**A.**
大枠は合っているが、正確な単位は「同じdocker-compose.ymlファイル」ではなく「同じdocker composeプロジェクト」。

`docker compose up`はプロジェクト専用のネットワークを1つ自動生成し(`<プロジェクト名>_default`)、`docker-compose.yml`内の全サービスをそこに参加させる。プロジェクト名のデフォルトは`docker-compose.yml`があるディレクトリ名なので、素朴には「同じymlファイル = 同じプロジェクト = 同じネットワーク」で合っている。

ズレるケース:

- 同じ`docker-compose.yml`でも`-p`で別のプロジェクト名を指定して2回起動すると、別々のネットワークになり通信不可になる
- `docker-compose.yml`と`docker-compose.override.yml`のように複数ファイルを`-f`で組み合わせて1つのプロジェクトとして起動すれば、ファイルは複数でも同じネットワーク
- `networks:`を明示的に定義し`external: true`で既存の外部ネットワークを指定すれば、別プロジェクト(別ファイル)のコンテナ同士でも同じネットワークに参加できる

## Q. 一度停止して再度`docker compose up`で起動すると、`curl http://localhost:8080`でのアクセスカウントが維持されているのはなぜか?

**A.**
「コンテナを削除したか、していないか」と「redisがデータをディスクに書き出しているか」の2つが絡んでいる。

`docker compose stop`はコンテナを停止するだけで削除はしない。

| コマンド | コンテナ | 中のファイル(`/data`など) |
|---|---|---|
| `docker compose stop` | 停止するが残る | 残る |
| `docker compose down` | 削除される | 消える(名前付きvolumeがない限り) |

「停止→再度`docker compose up`」では、既存の(停止していた)同じコンテナが再起動されるだけで、新しいコンテナは作られない。

`stop`はコンテナ内のredisプロセスに`SIGTERM`を送るためプロセス自体は一度終了するが、redisはデフォルト設定でディスクへのスナップショット保存(RDB)が有効になっている。

1. `stop` → redisが終了前に保存ポイントの設定に従いディスクへカウント値を保存
2. コンテナ自体は削除されていないので、保存先ファイルはそのままコンテナ内に残る
3. 再度`up` → 同じコンテナが再起動 → redis起動時に保存ファイルを読み込んでメモリに復元
4. `curl`で見えるカウントが継続している

もし`docker compose down`していたら、コンテナ自体が削除される。この設定は名前付きvolumeを使っていないため、保存ファイルを含むコンテナの中身も一緒に消え、次の`up`ではカウントが`1`から再スタートする。

## Q. スナップショット保存先はコンテナの`/data/dump.rdb`か?

**A.**
その理解で合っている。`redis:7-alpine`イメージを確認すると`WorkingDir`が`/data`に設定されている。

```json
"WorkingDir": "/data",
"Volumes": { "/data": {} }
```

redisのデフォルト設定では保存先ディレクトリ(`dir`)はカレントディレクトリ(`./`)、ファイル名(`dbfilename`)は`dump.rdb`なので、組み合わせると保存先は`/data/dump.rdb`になる。

さらに、上記の`"Volumes": { "/data": {} }`は`redis`イメージのDockerfile側で`VOLUME /data`が指定されていることを意味する。`docker-compose.yml`側で明示的に`volumes:`を書いていなくても、Dockerが自動的に匿名(anonymous)ボリュームを作り`/data`にマウントしている。

ただし匿名ボリュームは、名前付きボリュームと違って`docker compose down`時にコンテナと一緒に孤立・削除されやすい。確実にデータを残したい場合は明示的に名前付きボリュームを定義するのが一般的。

```yaml
services:
  redis:
    image: redis:7-alpine
    volumes:
      - redis-data:/data

volumes:
  redis-data:
```

こうしておけば`docker compose down`(`-v`なし)をしても`redis-data`という名前付きボリュームは残り、`up`し直せばデータが必ず引き継がれる。
