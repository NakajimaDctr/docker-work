## Q. `docker build -t counter-app .` は何をしている?

**A.**
カレントディレクトリの`Dockerfile`を元に、Dockerイメージをビルドするコマンド。

- `docker build`: Dockerfileからイメージを構築する
- `-t counter-app`: 出来上がるイメージに`counter-app`という名前(タグ)を付ける(`-t`は"tag"の略)
- `.`: ビルドコンテキストをカレントディレクトリに指定する。Dockerfileと、そこから`COPY`などで参照するファイル群をこのディレクトリから探す

「この場所にあるDockerfileの手順通りに、`counter-app`という名前のイメージを作って」という指示であり、この後`docker run --rm counter-app`でそのイメージからコンテナを起動する。

### ビルドコンテキストとは

末尾の`.`が指定しているのは、`docker build`実行時にDocker(正確にはDockerデーモン)へ送られる「ファイル群の集合」で、これを**ビルドコンテキスト**と呼ぶ。

Dockerfile内の`COPY`や`ADD`は、ホスト側のファイルをイメージに取り込む命令だが、この時に参照できるファイルは**ビルドコンテキストの中にあるものだけ**。

```dockerfile
COPY counter.py /app/counter.py
```

このとき`counter.py`は、ビルドコンテキスト(`docker build`実行時に指定したディレクトリ、通常は`.`)の直下にある必要がある。ビルドコンテキストの外にあるファイル(例えば`../other-dir/file.txt`のような親ディレクトリのファイル)は`COPY`できない。

```
docker build -t counter-app .
                            ↑
                    ビルドコンテキスト
                    (このディレクトリ以下を
                     Dockerデーモンに送信)
```

1. `docker build`を実行すると、指定したディレクトリ(`.`)以下の全ファイルがひとまとめに送信される
2. Dockerデーモンはその中から、Dockerfileの指示(`COPY`など)に従って必要なファイルを取り込みながらイメージを構築する

補足:
- ビルドコンテキストが大きい(不要なファイルが大量にある)と、ビルドのたびに送信に時間がかかる
- `.dockerignore`ファイルを使うと、`node_modules`や`.git`など不要なファイルをビルドコンテキストから除外できる(`.gitignore`と似た書き方)
- **ビルドコンテキスト**(どのディレクトリを送るか)と**Dockerfileの場所**(`-f`オプション)は別々に指定できる

## Q. `-v counter-data:/data` の `counter-data` と `/data` はそれぞれ何を指す?

**A.**
`-v`オプションの値は、コロン(`:`)で区切られた2つの要素からなる。

- **`counter-data`**(コロンの前・左側): マウント元。ここでは「使うボリュームの名前」。存在しなければDockerが自動作成する。
- **`/data`**(コロンの後・右側): マウント先。コンテナ内のパス(ディレクトリ)。

つまり`-v counter-data:/data`は「`counter-data`という名前のボリュームを、コンテナ内の`/data`につなぐ」という意味。

書式は`-v <ホスト側 or ボリューム名>:<コンテナ内のパス>`で、コロンの左が「外側(ボリュームやホストのディレクトリ)」、右が「内側(コンテナ内のパス)」という対応になる。バインドマウント`-v "$(pwd)/local-data:/data"`も同じ構造で、左側がボリューム名の代わりにホストの絶対パスになっているだけ。

## Q. `counter-data`はDocker(ホスト)側の元容量、`/data`はコンテナ内のパスという理解で合ってる?

**A.**
大枠は合っているが、「ホスト側」という表現には補足が必要。

- **`counter-data`**: Dockerが管理する**名前付きボリューム**。データの実体はホストPCのディスク上のどこかに保存されるが、保存場所はDockerが管理しておりユーザーが直接パスを意識する必要はない(「このデータの置き場所は任せて」という方式)。
- **`/data`**: コンテナ**内部**から見えるパス。コンテナのプロセス(`counter.py`)はこの`/data`というパスを通してファイルを読み書きする。

「`counter-data`がデータの実体を保持する場所、`/data`がコンテナ内からそこにアクセスするための入り口」という理解であれば正確。

なお、バインドマウント(`-v "$(pwd)/local-data:/data"`)の場合は左側が「ホストPC上の具体的なディレクトリパス」になるため、その場合は文字通り「ホスト側のパス」と呼べる。ボリュームの場合は「Docker管理の保存領域」、バインドマウントの場合は「ホストの実パス」と使い分けると正確。

## Q. `$(pwd)` とは何か? ホスト側の今いる場所を指す?

**A.**
`$(pwd)`は、シェル(bash/zshなど)の**コマンド置換**という機能。

- `pwd`は"print working directory"の略で、**現在いるディレクトリの絶対パス**を表示するコマンド。
- `$( ... )`は、中のコマンドを実行して、その**出力結果を文字列としてその場に埋め込む**という書き方。

`docker run`コマンド自体は、コンテナの中ではなく**ホスト側のシェル(ターミナル)**で実行されている。`$(pwd)`はそのDockerコマンドが実行される**前**に、シェルによって評価・置換されるため、これは常に「ホストPC上で、今自分がいるディレクトリの絶対パス」を指す。

例えば`exercises/04-volumes-and-data`にいるときに

```bash
docker run --rm -v "$(pwd)/local-data:/data" counter-app
```

を実行すると、シェルはまず`$(pwd)`の部分を実際のパスに置き換えてから、Dockerにコマンドを渡す。実質的には次のように解釈される。

```bash
docker run --rm -v "/Users/keisuke/Desktop/docker-work/exercises/04-volumes-and-data/local-data:/data" counter-app
```

READMEのトラブルシューティング欄にある「`-v`のホスト側パスは絶対パスが必要」というルールに対応するためのテクニックで、相対パス(`./local-data`など)をそのまま`-v`に渡すとうまく動かないことがあるため、`$(pwd)`でその場で絶対パスに変換してから渡している。
