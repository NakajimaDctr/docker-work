## Q. 「Docker内蔵のDNSによる名前解決」とは?

**A.**
Dockerには内蔵の**DNSサーバー**があり、`docker network create`で作った**ユーザー定義ネットワーク**に参加しているコンテナ同士は、IPアドレスではなく**コンテナ名**で相手を見つけて通信できる。

- 例: `web`という名前のコンテナに対し、同じネットワークの別コンテナから`http://web`や`ping web`のように名前だけでアクセスできる
- コンテナのIPアドレスが再起動のたびに変わっても、名前さえ変わらなければ通信先を書き換える必要がない
- **既定の`bridge`ネットワークではこの名前解決が効かない**。名前解決を使いたい場合は自分で`docker network create`したネットワークに参加させる必要がある(Docker Composeはこれを内部的に自動でやってくれる)

### 注意点: `ping`は誤解を招くことがある

`bridge`のようなコンテナ名DNS解決が効かないネットワークで存在しない/届かない相手に`ping -c 3 web`を試すと、`127.0.53.53`という特殊なダミーIPへの応答で「成功」してしまうことがある。`127.x.x.x`はどのコンテナから見ても自分自身のループバックを指すため、`ping`は常に応答してしまう。これは「`web`という名前のコンテナはどこかに存在するが、今の接続元からは到達できない」ことを示すシグナルであり、実際に到達できているかは`wget`などHTTP通信で確認するのが確実。

## Q. `docker run --rm alpine wget -qO- --timeout=3 http://web` の意味は?

**A.**
`docker run`部分と、コンテナ内で実行される`wget`部分に分けて読む。

| 部分 | 意味 |
|---|---|
| `docker run --rm alpine` | `alpine`イメージから使い捨てコンテナを起動し、終了後に自動削除する |
| `wget` | HTTPリクエストを送るコマンド |
| `-q` | quietモード(進捗表示を出さない) |
| `-O-` | 取得結果の出力先を指定するオプション。`-`(ハイフン)を指定するとファイル保存せず標準出力にそのまま出す |
| `--timeout=3` | 接続待ちのタイムアウトを3秒に設定 |
| `http://web` | アクセス先。IPアドレスではなく**コンテナ名**`web`を使っている点がこの章のポイント |

「`alpine`という使い捨てコンテナを起動し、その中から`web`という名前のコンテナにHTTPリクエストを送り、結果を画面に出す」という一連の処理。

## Q. `docker run <イメージ> <コマンド>`のように、コンテナ起動と同時にコマンドを実行する手法は05章より前に説明があった?

**A.**
はい。03章(Dockerfileの基本)で、`CMD`/`ENTRYPOINT`の上書きの文脈ですでに登場している。

```bash
docker run image          # → python hello.py が実行される(CMDのデフォルト)
docker run image echo hi  # → CMD全体が丸ごと echo hi に置き換わる
```

ただしそのときの主眼は「Dockerfileのデフォルトコマンドが実行時引数でどう変わるか」。05章のように、汎用ツール入りのイメージ(`alpine`)に対して疎通確認用のコマンド(`wget`, `ping`)を都度渡すという応用的な使い方は05章で初めて登場する。

## Q. 手順1「まずはネットワークなしで失敗を体験する」が失敗するのは、`bridge`という既定のネットワークに参加しているから?

**A.**
その理解でおおむね正しいが、重要な補足がある。手順1の2つのコンテナはどちらも`--network`を指定していないため、**同じ`bridge`(既定のネットワーク)に参加している**。つまり「別々のネットワークにいるから失敗する」のではなく、**同じネットワークにいるのに失敗する**、という点がこのハンズオンのポイント。

失敗の理由は、`bridge`が**コンテナ名による名前解決の機能自体を持っていない**ため。`bridge`はコンテナ同士の通信(IPアドレス指定なら)自体は可能だが、Docker内蔵DNSによる名前解決は`docker network create`で作ったユーザー定義ネットワークでのみ有効になる。

## Q. 手順1と手順3で疎通確認のコマンド(`wget`/`ping`)が異なるのはなぜ?

**A.**

| 手順 | ネットワーク | コマンド | 結果 |
|---|---|---|---|
| 1 | `bridge`(既定) | `wget http://web` | 失敗 |
| 3 | `my-net`(作成したもの) | `ping -c 3 web` | 成功 |
| 4 | `my-net`(作成したもの) | `wget http://web` | 成功 |

- **手順1が`wget`な理由**: `bridge`上で`ping`を使うと、Docker内蔵DNSが返す`127.0.53.53`というダミーIPへの応答で「成功」してしまい、実際には到達できていないのに誤解を招く。確実に失敗を示すため、実際のHTTP到達性を見る`wget`を使っている。
- **手順3が`ping`な理由**: 正しく`my-net`に参加した状態で同じ`ping -c 3 web`を実行すると、今度は本物の`web`コンテナのIPアドレスに実際に到達して真に成功する。「見せかけの成功(手順1で`ping`を試した場合)」と「本物の成功(手順3)」の違いを体感させる対比になっている。
- **手順4が`wget`な理由**: 手順3の`ping`はICMPレベルの疎通確認にとどまるため、手順4ではHTTPレベルで実際にnginxのレスポンス(HTML)を取得できることまで確認し、「名前解決 → ネットワーク到達性 → アプリケーションレベルの通信」と段階的に確認レベルを上げている。

## Q. 疎通確認は`alpine`→`web`(nginx)の一方向で検証している? 手順4の見出し「コンテナ内からHTTP通信も」の"コンテナ内から"は手順3と何が違う?

**A.**
方向についてはその理解で合っている。`--rm`で使い捨ての`alpine`コンテナが**クライアント役**、`--name web`で起動され続ける`nginx`コンテナが**サーバー役**であり、`web`側から`alpine`にアクセスする手順はない。

見出しの"コンテナ内から"については鋭い指摘の通り。手順3・手順4はどちらも`docker run --rm --network my-net alpine ...`という同じ形で、"コンテナ内から"という点自体は手順3との対比では新しい要素ではない。見出しが強調したいのはおそらく"コンテナ内から"ではなく**"HTTP通信も"**の部分で、手順3までのICMP(`ping`)レベルの確認から、手順4でHTTPレベルの確認へと引き上げていることを表していると考えられる。

## Q. 手順5「ネットワーク詳細を確認する」の結果に`alpine`が表示されず`web`しか表示されないのは、`wget`実行後にコンテナが停止したから?

**A.**
「停止」ではなく**「削除」**されたから、というのがより正確な理由。実際に検証すると次のようになる。

- `alpine`が実行中(`docker run -d --rm --network my-net alpine sleep 5`のような状態)は`docker network inspect`に`web`と一緒に表示される
- `alpine`が終了して`--rm`により**コンテナ自体が削除される**と、そのネットワークへの接続(エンドポイント)も一緒に消え、`docker network inspect`から消える

05章のコマンドは`docker run --rm ... alpine wget ...`と`--rm`オプション付きのため、コンテナは終了と同時に削除される。もし`--rm`を付けずに実行していたら、コンテナは「停止状態」として残り続け、`docker network inspect`にもIPアドレス付きで表示され続けたはずである。
